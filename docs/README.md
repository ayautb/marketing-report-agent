# Report Runway v2 — внутренний маркетинговый отчёт

Автономный проект на основе согласованных требований. Интерфейс на английском; внешний сервис, Lovable, Supabase, AI и LibreOffice для работы не нужны.

## Быстрый запуск на Mac

1. Распакуй архив.
2. Открой `Start.command`.
3. Открой `http://127.0.0.1:4317`.
4. Создай первый аккаунт парт-лидера. После входа в **Team access** создай три аккаунта менеджеров и назначь направления.

Если предыдущая копия уже работает, останови её через Ctrl+C в её окне запуска, затем открой `Start.command` из обновлённой папки. Для нового результата нужна новая генерация; файлы прошлых отправленных версий не меняются. При замене установленной папки сохрани её прежний `data/` (или настроенный DATA_DIR), чтобы продолжить с теми же аккаунтами и проектами.

На сервере нужны **Node.js 24+** и **Python 3.9+**. Скрипт для Mac использует доступный Node или встроенный runtime ChatGPT, если тот есть; Python должен быть уже доступен. Установка npm/pip-зависимостей не требуется. Не открывай `public/index.html` напрямую.

Другой запуск: `node server.mjs`. Для v2 используй отдельный DATA_DIR; автоматический импорт базы v1 не предусмотрен.

**В текущем комплекте скачивание PPTX и HTML работает. Финальная отправка требует подключения разрешённого внутреннего компонента отображения PPTX. До подключения показано честно обозначенное приближённое превью, а Submit заблокирован на сервере.**

## Процесс менеджера

**Projects → Project form → Evidence → Slide composer → Generate → Preview → Submit.**

- Каждый менеджер видит только свои проекты. Лидер не имеет доступа к черновикам и их вложениям.
- Для каждого проекта сохраняются месячные обновления. При продолжении проекта переносятся основные сведения; результаты, период, evidence и значения KPI нового месяца заполняются заново.
- Черновик автоматически сохраняется при вводе. Есть явное сохранение и защита от перезаписи из другого окна.
- Обязательны название, страна, категория, партнёр, цель, период, каналы, работы месяца, вывод, next steps и 1–6 изображений. Для N/A партнёра нужно пояснение. Trade/Affiliate требуют KPI план/факт/единица. Retail требует общий статус и этап Design/Bidding/Production/Installed.
- Текстовые блоки до 150 символов. Название до 80, heading до 60, subtitle до 100. Это ограничения ввода, а не доказательство размещения в любом макете: финальное превью нужно проверить.
- Группа evidence имеет общий heading/subtitle. Для изображений доступны показ целиком, автоматическая и ручная обрезка. Оригиналы сохраняются. Низкое разрешение даёт предупреждение.
- Для общего Executive summary менеджер выбирает один главный проект своего направления; для общего Next steps — один проект независимо от первого выбора. Текст пишет менеджер. Второй выбранный проект в том же разделе нужно снять перед генерацией. Для выбранного Next steps суммарный текст действий, ответственных и сроков — до 150 символов, чтобы он помещался в одну карточку последнего слайда.
- В **Slide composer** выбираются исходный макет, проекты на слайде и порядок слайдов. Один элемент плана создаёт один проектный слайд. При нехватке места нужно выбрать более вместительный исходный макет или явно разделить проекты в плане.
- Генерация создаёт неизменяемую сборку. Изменение черновика после генерации делает её непригодной для новой отправки: нужно создать и проверить следующую сборку.
- После Submit создаётся V1/V2/...; предыдущая отправленная версия не меняется. Правки продолжаются в отдельном черновике.

Один активный менеджер на направление. При замене сотрудника лидер отключает старый аккаунт и создаёт новый. Автоматическая передача чужих проектов новому аккаунту не реализована.

## Процесс парт-лидера

**Submitted reports → Preview → Accept → Generate combined report → Download PPTX / Download HTML / Copy for email.**

- Лидер видит только отправленные версии и их историю.
- Принимается последняя отправленная версия менеджера. Возврат с комментариями и уведомления не предусмотрены.
- Общий выпуск формируется из последних принятых версий по направлениям в порядке **KZ ATL/BTL → 4CA Marketing → KZ Retail**.
- Если новая версия ещё не принята, остаётся предыдущая принятая; интерфейс предупреждает об этом.
- Неполный выпуск разрешён. Отсутствующие направления перечисляются в PPTX и HTML.
- Состав каждого выпуска фиксируется в момент создания. Последующие правки проектов не изменяют ранее созданные файлы.
- Письмо отправляется вручную. Приложение ничего не отправляет.

## PPTX и шаблон

`templates/high-technology-gsl.pptx` — оригинальный предоставленный файл. Генератор копирует его OOXML-слайды, сохраняя их мастер, макеты, медиа, порядок объектов, группы и видимые стили. Это не отрисовка слайдов заново на основе скриншотов.

Общая структура: титульный слайд → один общий Executive summary (слайд 2) → проектные слайды по планам трёх направлений → один общий Next steps (последний слайд). Summary и Next steps не повторяются внутри направлений. Отсутствующее направление отмечается в общем summary без дополнительного слайда.

Поддержаны все 10 семейств композиций исходника: обложка, summary, Premium/Step Up, promo/KPI, grouped content, launch, retail pipeline, collage, retail project, next month. Для KZ и 4CA используются соответствующие исходные варианты.

Редактируются существующие текстовые блоки и привязки изображений. Неиспользуемые evidence-области скрываются. Дополнительные Project Brief и KPI-слайды автоматически не добавляются. Проектные слайды определяет только план менеджера. Нехватка места в выбранном макете вызывает понятную ошибку вместо создания незапрошенных продолжений. Отдельный график появляется только при явно включённой опции editable KPI chart.

Если включён editable KPI chart, график создаётся отдельным native chart-объектом в дополнительной копии исходного promo-слайда, со встроенной XLSX-таблицей. Исходное evidence не заменяется графиком. Для графика требуется единая единица измерения; для смешанных единиц используй отдельные изображения графиков. Загруженный график-картинка остаётся картинкой.

Шрифты **Instrument Sans** и **Google Sans**, включая курсивные variable TTF, лежат в `fonts/` вместе с OFL-лицензиями, источниками и SHA-256. Они не устанавливаются на ПК автоматически и не встроены в выходной PPTX. Для совпадения отображения шрифты должны быть доступны на сервере рендеринга и в корпоративном PowerPoint. Helvetica не упакована.

**Экспорт структурно проверен. Полная визуальная идентичность, отсутствие переполнения при любом тексте и совместимость редактирования в конкретной корпоративной версии PowerPoint ещё требуют проверки в этой среде.**

## HTML

Создаются `summary.html` и `email.html`. Первый — самостоятельный документ, второй — HTML-фрагмент с inline-стилями для письма. Содержание одинаковое: общий Executive summary → Main results со всеми проектными слайдами как инфографикой в порядке готового PPTX → общий Next steps с владельцами/сроками. Избранное влияет только на общие таблицы, все проектные слайды остаются в Main results. Изображения встроены в HTML; отдельная папка картинок не нужна. При подключённом утверждённом renderer используются его PNG из готового PPTX; без него — те же SVG приближённого превью, что и в приложении. Все пользовательские строки экранируются. В самостоятельном HTML и email-фрагменте используются тёмный фон, оригинальный glow-asset, синие градиенты/акценты шаблона и встроенный Instrument Sans. Табличная структура сохранена. Месяц на обложке PPTX и в HTML отображается как November 2026; технический ключ месяца остаётся 2026-11.

Референс для общих Executive summary и Next steps — **1080 × 1440**. Для этих блоков сохранён лимит 10 строк и 1 400 символов; в браузере проверяется их суммарная высота. Main results занимает столько места, сколько требуется всем проектным слайдам: полный HTML прокручивается вертикально. Ничего не удаляется и не сокращается автоматически. В почтовом клиенте внешний вид нужно проверить после вставки.

## Точное превью без LibreOffice

Переменная `RENDERER_COMMAND` задаёт абсолютный путь к утверждённому IT исполняемому компоненту. Сервер вызывает его **без shell**, передавая два аргумента:

1. абсолютный путь к сгенерированному `report.pptx`;
2. абсолютный каталог для результата.

Компонент должен создать каталог и PNG `slide-1.png`, `slide-2.png`, ... строго для всех слайдов. Код завершения 0, лимит 120 секунд. Файлы остаются внутри корпоративной среды. Возвращаемые изображения должны быть получены отображением именно этого PPTX со всеми требуемыми шрифтами. Компонент не должен обращаться к публичным конвертерам.

Без этого компонента создаётся SVG-превью из XML готового PPTX. Оно помогает проверить содержание и раскладку, но имеет ограничения по маскам, эффектам, встроенным графикам, переносам и метрикам текста. Оно не считается точным. Код не содержит пользовательского переключателя для обхода проверки. Доверие к выбранному renderer — зона ответственности IT; наличие PNG само по себе не доказывает тождественность PowerPoint.

## Внутреннее размещение

Пример переменных окружения:

```sh
HOST=0.0.0.0 PORT=4317 APP_ORIGIN=https://reports.company.internal DATA_DIR=/srv/runway/data PYTHON_BIN=/usr/bin/python3 RENDERER_COMMAND=/opt/company/pptx-renderer node server.mjs
```

Нужен HTTPS reverse proxy, сохраняющий Host. Node-порт не открывать публично. `APP_ORIGIN` включает Secure-cookie и отключает первичную регистрацию через браузер. Первый аккаунт создаётся через `node manage.mjs create-user`: JSON по stdin с полями email, name, role=leader, password. Пароли не помещать в аргументы команд или файлы проекта. Менеджеру дополнительно нужен `team`.

Dockerfile — пример упаковки для IT. Он устанавливает Node/Python/fontconfig и шрифты внутри серверного образа. Настройка сети, HTTPS, постоянного диска и renderer остаётся за IT. Docker-образ в среде разработки не собирался.

Вход пока через отдельные аккаунты; корпоративный SSO/Knox не подключён. AI/API-ключи не используются и не запрашиваются. Подключение AI потребует отдельного утверждённого внутреннего решения.

## Хранение, резервные копии и срок

`DATA_DIR` содержит SQLite, оригиналы evidence и неизменяемые сборки. Из коробки база и файлы не зашифрованы приложением; шифрование диска и резервных копий настраивает IT. Доступ защищают серверная авторизация, роли, cookie-сессии, CSRF и права файлов. Сессии отзываются при отключении аккаунта.

Срок для сборок — 365 дней. Ежемесячные черновики очищаются по границе месяца годичной давности. Для выполнения политики IT запускает обслуживание при остановленном приложении:

```sh
node maintenance.mjs purge
node maintenance.mjs purge --apply
node maintenance.mjs backup /absolute/new-backup-directory
```

Первая команда только показывает объём удаления. Вторая удаляет истёкшие сборки, старые обновления и ненужные изображения, сохраняя файлы, которые нужны актуальным черновикам/версиям. Расписание здесь не устанавливается. Для восстановления остановить сервер и вернуть всю папку data из одной согласованной резервной копии. Проверить восстановление на отдельном стенде. Команда backup не шифрует копию.

## Проверки

```sh
node --test test/workflow.test.mjs
python3 test/test_export.py
```

Проверяются авторизация, приватность, CSRF, обязательные поля, владение evidence, версии, optimistic locking, блокировка неточного/устаревшего превью, принятие, неполный выпуск, защита HTML, retention, целостность OOXML-ссылок, исходный порядок объектов, группировка 4+2 изображений и встроенная таблица графика.

Дополнительно проверены живые HTTP-запросы и браузерный вход, ввод/автосохранение, генерация, превью HTML с таблицами и контроль его высоты. Загрузка через браузерный file chooser не завершилась из-за потери вкладки; загрузка и привязка изображения проверены через настоящий HTTP API. Корпоративный PowerPoint и точный renderer ещё не проверены. Тестовые аккаунты и данные в архив не включены.
